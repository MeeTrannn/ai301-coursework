# Rubric: is this pull request ready to submit?

Each check reads the PR package against the plan it claims to
implement and the issue that plan belongs to. Locations for every
evidence source are in `references/evidence-guide.md`; the order to
gather them in is in `procedure.md`. A shortfall the PR discloses
(in the plan's deviation notes, or plainly in the description) is
honest and can pass; only a silent gap fails.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `scope_fidelity` | The diff's changed files and hunks, read against the plan's stated boundary (its scope pair: what is in, what is out) and its deviation notes. | Every changed file sits inside the plan's boundary, is a test the plan's test plan names, is an artifact the repo's stated asks require (a changelog entry; removing an `xfail` marker or a test suppression that names this issue), or is explained by a deviation note. Nothing the plan puts out of scope appears. Every change the plan commits to is in the diff, or its absence is disclosed in a deviation note or the description. Fail on any file or hunk outside that set, or any planned change missing with no disclosure. | required |
| `description_truth` | Every factual claim in the PR title, description (including its list of changes), and checklist ticks, read against the diff. | Every claim about what the PR changes, adds, or leaves alone is visible in the diff: a claimed file, test, or entry is there, and a claimed non-change ("no options added", "X unaffected") is not contradicted by any hunk. Every change in the diff is listed in the description's changes. A fidelity claim ("implements the plan exactly", "no changes beyond it") passes only if `scope_fidelity` passes. Claims about test results are graded by `evidence_observable`, not here. Fail on any claim the diff contradicts or does not show, or any diff change the description leaves out. | required |
| `test_plan_coverage` | Each case the plan's test plan names, read against the test files and fixtures in the diff. | Every case the plan says to add as a new test or fixture has one in the diff that encodes it, or the PR discloses that it is not covered and why. Cases that are runs rather than new tests (re-running the repro, a control that should stay unchanged, running an existing suite or spec) are covered when the test evidence reports running them; they need no new file in the diff. Fail on any planned new test or fixture that is silently missing. | required |
| `evidence_observable` | The test-evidence section, read against the plan's test plan, the issue's reproduction steps, and the checks the repo's PR template or contributing guide lists. | (1) Decisive repro: the reproduction the issue or plan names (the input that actually breaks, not a control or an unchanged path) is re-run on the branch, with its command or input shown and both its before result (default branch or the earlier repro output) and its after result shown. A transcript or code block with the before and after results annotated inline counts as pasted output. The after shows the expected behavior the issue or plan names. When the plan names more than one failure mode or repro, each is re-run. (2) Supporting checks (the test suite, lint, format, typecheck, controls): a one-line result that names the specific command or check and its outcome ("`cargo test -p ignore` passes (214 tests)", "fmt and clippy clean", "no-ampersand control unchanged") is enough once (1) holds; full raw output is not required for these. A failing check passes when the PR states the reason. Fail when the repro is never re-run or has no before/after ("works on my machine", "colors work now", "verified for a day"), when the evidence exercises only a control or the unchanged path instead of the broken one, when one of the plan's named repros is silently not re-run, when a `[paste output here]` placeholder is left in, or when pasted output shows a failure the PR does not disclose. | required |
| `diff_clean` | The unified diff's hunks and the commit list. | Every hunk serves the fix, its tests, or a repo-required artifact. Fail on any debug leftover (print or log calls added for debugging), commented-out code, dead code, whitespace or formatting churn on lines the fix does not touch, drive-by edits unrelated to the issue, or stray files (the contributor's own drafts such as `plan.md`, `pr_draft.md`, `test_evidence.md`, or `comment.md`; local config; editor or OS files; an unrequested lockfile change). | required |
| `template_complete` | The repo's PR template sections and stated contribution and AI-use policy, read against the PR description. | Every section the template defines is present with content specific to this PR ("N/A" with a reason counts). The issue reference names this issue: any clear reference (`Closes #n`, `Fixes #n`, or `#n` cited in the description) counts, unless the template or guide demands a specific form, in which case that form is required. Every explicit PR ask in the contributing guide is met. A ticked checklist box is true; an unticked box for work that has not happened (such as CI, which runs only after the PR opens) is correct, not a gap. Treating the package as AI-assisted, an AI-use disclosure in the contributor's own words is present wherever the repo's or course's policy asks for one. If the repo states no template and no policy, pass and say so in the evidence line. Fail on a missing section, a section left as template boilerplate, or a missing required disclosure. | required |

## Verdict rule

Accept (submit) only if every check above grades `pass`. If any check
grades `fail` or `unclear`, reject (hold). `unclear` counts as fail: a
PR whose readiness cannot be verified from the package is not ready
to submit. There are no preferred checks; every check can hold the
package.
